# GIF 영역 캡처: 설계 스케치

상태: 초안. 용도, 커서, 시작/종료/취소 방식은 확정(2026-11-20, 사용자 결정). 구현 스택은 Tauri 2(Rust 코어 + 웹 UI)로 확정.
대상 OS: Windows 10 19045 이상.
**용도**: 재생 중인 영상의 일부를 잘라 짤(GIF)로 만드는 것. 녹화하는 동안 영역 안에서 조작은 없다고 가정.

## 1. 사용자 흐름

시작과 종료 방식은 설정의 `recordControl`로 고르며, 시작 방식마다 짝이 되는 종료 방식이 정해져 있습니다.

```
                          ┌─ immediate ─────────────────────────→ Recording ─(Enter)─┐
Idle ─(선택 시작)→ Selecting ─(드래그 완료)┤                                                     ├→ Encoding → Done
                          └─ button ─→ Armed ─([시작] 클릭)→ Recording ─([끝] 클릭)───┘
         ▲                │ Esc            │ Esc              │ Esc (스풀 폐기)
         └────────────────┴────────────────┴──────────────────┘
```

| `recordControl` | 시작 | 종료 |
|---|---|---|
| `immediate` | 드래그를 마치는 순간 | Enter |
| `button` | 영역 밖에 뜨는 [시작] 버튼 클릭 | 같은 버튼이 [끝]으로 바뀜 → 클릭 |

**영역을 정하는 방식**은 설정의 `selection`으로 고릅니다.

| `selection` | 영역 정하기 |
|---|---|
| `drag` | 단축키 → 화면이 어두워짐 → 드래그 (위 흐름 그대로) |
| `frame` | 단축키 → 지난번 위치와 크기 그대로 **녹화 틀**이 뜸(Selecting을 건너뛰고 바로 Armed) → 틀의 상하좌우 가장자리를 끌어 크기를 바꾸거나 틀을 옮김 → [시작] 클릭 |

- `frame`에서는 드래그가 없으므로 `recordControl`이 `immediate`여도 시작은 [시작] 버튼입니다. 종료는 `recordControl`을 따릅니다(`immediate`면 Enter, `button`이면 [끝]).
- Armed 동안에는 틀을 옮기거나 크기를 바꿀 수 있고(`RegionChanged`), 녹화가 시작되면 영역은 고정됩니다. `drag` + `button` 조합에서도 Armed 동안 같은 방식으로 영역을 다듬을 수 있습니다.
- 틀은 영역 바깥에 그리는 테두리와 손잡이로 이루어지고 `WDA_EXCLUDEFROMCAPTURE`로 캡처에서 빠집니다. 틀 안쪽은 클릭이 통과해서 영상 플레이어를 그대로 조작할 수 있습니다.

- Esc는 인코딩 전의 모든 단계(Selecting, Armed, Recording)에서 취소입니다. 두 모드 공통이고, Recording에서 취소하면 쌓인 프레임을 버리고 Idle로 돌아갑니다.
- `button` 모드에서는 [끝] 옆에 [✕] 버튼도 둡니다(마우스로 쓰는 모드라서).
- 최대 녹화 길이(`maxDurationSec`)에 도달하면 종료한 것과 똑같이 인코딩합니다. 녹화를 잊어버렸을 때를 위한 안전장치입니다.
- 결과는 파일로 저장하고, 설정에 따라 클립보드에 복사합니다(CF_HDROP).
- **커서는 GIF에 찍지 않습니다.**

## 2. 이 기능이 건드리는 시스템

| 시스템 | 결정해야 할 것 / 함정 |
|---|---|
| 선택 시작 진입점 | 앱이 트레이에 떠 있는 동안 전역 단축키(`beginSelectionHotkey`, 기본 `Win+Shift+G`)를 누르면 바로 선택 오버레이가 뜸. Windows의 Win+Shift+S와 같은 사용감. `RegisterHotKey`가 실패하면(다른 프로그램이 이미 사용 중) 알리고 설정에서 바꾸게 함. 호스트 앱의 버튼으로도 시작 가능 |
| 선택 오버레이 | 최상위 투명 창. 모니터별 DPI(Per-Monitor v2): 논리 좌표와 물리 좌표 변환을 여기서 딱 한 번만 함 |
| 화면 캡처 | DXGI Desktop Duplication. DXGI는 커서를 원래 포함하지 않으므로 커서 제외는 공짜. 화면이 바뀔 때만 프레임이 오므로 타임스탬프로 프레임 간격을 정함 |
| Enter 종료 (`immediate`) | 녹화 중에만 수정키 없는 `RegisterHotKey(VK_RETURN)`을 등록하고, 끝나면 해제. **Enter가 영상 플레이어로 가지 않고 가로채짐**(일부 플레이어는 Enter가 전체 화면 전환이라 중요함) |
| Esc 취소 | Selecting, Armed, Recording 동안 `RegisterHotKey(VK_ESCAPE)`를 등록. 포커스가 영상 플레이어에 있어도 동작함. 플레이어의 Esc(전체 화면 해제 등)도 가로채므로 녹화 중 화면이 갑자기 바뀌지 않음 |
| [시작]/[끝] 버튼 (`button`) | 클릭 통과가 아닌 작은 최상위 창. `WDA_EXCLUDEFROMCAPTURE`로 캡처에서 빠지므로 영역과 겹쳐도 GIF에 찍히지 않음. 영역 밖에 둘 자리가 없으면(전체 화면 영역) 영역 안쪽 모서리에 둠 |
| 녹화 중 표시 | 영역 바깥 테두리. 클릭 통과 + `WDA_EXCLUDEFROMCAPTURE` |
| 프레임 저장 | 해상도 축소는 캡처 단계에서 적용. 메모리 상한을 넘으면 임시 파일로 넘김 |
| GIF 인코딩 | 영상은 그라데이션이 많아서 디더링 품질이 체감 화질을 좌우함. 카메라가 움직이면 프레임 간 차분 효과가 작아 용량이 큼 → 최대 용량 모드가 중요. 라이선스 주의: gifski는 AGPL, ImageSharp는 매출 조건부 상용 라이선스 |
| 설정 | 녹화 시작 시점의 설정을 스냅샷으로 떠서, 녹화 도중 바꿔도 진행 중인 세션에는 영향 없음 |

## 3. 두 가지 형태

### A. 녹화 → 봉인 → 일괄 인코딩 (선택)
캡처한 프레임을 스풀에 쌓기만 하고, 종료하면 봉인한 뒤 인코더가 전체를 한 번에 처리합니다.
- 전체 프레임을 보고 전역 팔레트를 만들 수 있어 화질이 가장 좋음
- 최대 용량 모드가 가능함: 결과가 크면 설정을 낮춰 다시 인코딩
- 인코더가 순수 함수라서 테스트하기 쉬움
- 대신 종료 후 인코딩 대기 시간이 있음(진행률 표시로 보완)

### B. 스트리밍 인코딩
프레임이 들어오는 즉시 인코딩해, 종료 직후 바로 결과가 나오는 방식입니다. 이미 쓴 프레임은 되돌릴 수 없어서 최대 용량을 보장할 수 없고, 프레임별 지역 팔레트를 쓰게 되어 화질도 떨어집니다.

**A를 고른 이유**: "용량 설정" 요구사항은 B로는 정직하게 구현할 수 없습니다.

## 4. 타입 스케치 (스택 중립 의사코드)

```ts
// 호스트 앱이 아는 유일한 표면
interface GifCaptureFeature {
  beginSelection(): void          // 호스트의 단축키나 버튼이 호출. Idle일 때만 의미 있음
  readonly state: Observable<SessionState>
}

type SessionState =
  | { kind: 'idle' }
  | { kind: 'selecting' }
  | { kind: 'armed'; region: ScreenRect }                    // button 모드에서만 거침
  | { kind: 'recording'; region: ScreenRect; startedAt: Instant; frameCount: number }
  | { kind: 'encoding'; progress: number }                   // 0..1
  | { kind: 'done'; file: OutputFile }
  | { kind: 'failed'; error: CaptureError }

// UI 부품(오버레이, Enter 핫키, 버튼)은 이벤트만 보낸다. 상태는 Session만 바꾼다.
type SessionEvent =
  | { kind: 'regionSelected'; region: ScreenRect }
  | { kind: 'startClicked' }
  | { kind: 'stop' }              // Enter든 [끝]이든 최대 길이 도달이든 같은 이벤트
  | { kind: 'cancel' }            // Esc 또는 [✕]. selecting, armed, recording에서 유효

// 물리 픽셀 기준, 한 모니터에 고정. v1에서는 여러 모니터에 걸친 영역을 시작 모니터 경계로 잘라냄.
type ScreenRect = { monitor: MonitorId; x: number; y: number; width: number; height: number }

type RecordControl = 'immediate' | 'button'   // 시작과 종료가 짝으로 묶여 있으므로 설정 하나

type GifSettings = {
  beginSelectionHotkey: Hotkey   // 수정키가 하나 이상 필요. Enter와 Esc는 고를 수 없음 (구현: crates/gif-core/src/hotkey.rs)
  selection: 'drag' | 'frame'    // frame이면 마지막 틀 위치와 크기도 함께 저장
  recordControl: RecordControl
  capture: { fps: GifFps; scale: number; maxDurationSec: number }
  encode: EncodeSettings
  output: { dir: Path; copyToClipboard: boolean }
}

// GIF 프레임 지연은 1/100초 단위이고, 브라우저는 0.02초 미만 지연을 0.1초로 늘려 버림 → 최대 50fps
// 설정에서 고를 수 있는 값은 10, 15, 30 (구현: crates/gif-core/src/fps.rs)
type GifFps = 10 | 15 | 30

// "열화 정도"와 "용량"은 동시에 지정할 수 없음 → 둘 중 하나만 고르는 합 타입
type EncodeSettings =
  | { mode: 'manual'; colors: number /*16..256*/; dither: number /*0..1*/; lossy: number /*0..100*/ }
  | { mode: 'maxSize'; maxBytes: number }   // 결과가 크면 lossy → colors → scale → fps 순으로 낮춰 재인코딩

interface FrameSource {                    // 구현은 DXGI 하나
  open(region: ScreenRect, opts: GifSettings['capture']): FrameStream
}
interface FrameStream { next(): Frame | 'end'; close(): void }
type Frame = { pixels: RgbaImage; timestampMs: number }   // scale 적용 완료, 커서 없음

interface FrameSpool {
  append(f: Frame): void
  seal(stopAtMs: number): SealedFrames     // stop 시각 이후 프레임은 버림
  discard(): void                          // cancel 시 메모리와 임시 파일을 모두 정리
}

// 순수 함수. 프레임 지연은 반올림 오차를 누적해 보정함(30fps → 3,3,4 / 100초 반복)
function encodeGif(frames: SealedFrames, s: EncodeSettings, onProgress: (p: number) => void): Promise<Bytes>
```

### 구현 현황

- `crates/gif-core/src/session.rs`의 `step(state, event, control)`이 위 전이 규칙을 순수 함수로 구현합니다. 해당하지 않는 이벤트는 상태를 바꾸지 않습니다.
- 스케치와 다른 점: 선택 시작을 `BeginSelection` 이벤트로 넣었습니다(스케치에서는 `beginSelection()` 호출).
- `crates/gif-core/src/writer.rs`의 `write_gif`가 팔레트 인덱스 프레임을 LZW로 압축해 GIF89a 파일로 씁니다. 두 번째 프레임부터는 바로 앞 프레임과 달라진 픽셀만 담습니다(`crates/gif-core/src/diff.rs`): 달라진 픽셀을 모두 감싸는 가장 작은 사각형만 쓰고, 그 안에서 안 변한 픽셀은 투명 번호로 채웁니다. 손실 압축은 이후 단위입니다.
- 투명 번호 한 자리를 비워 두어야 해서 팔레트는 최대 255색입니다(`Palette::MAX_COLORS`, `write_gif` 모두).
- `crates/gif-core/src/palette.rs`의 `Palette::from_frames`가 모든 프레임의 색을 중앙값 분할(median cut)로 최대 256색까지 줄여 전역 팔레트를 만들고, `to_indices`가 픽셀마다 가장 가까운 팔레트 색 번호를 고릅니다.
- `crates/gif-core/src/dither.rs`의 `ordered_dither`가 위치 고정 패턴(Bayer 8×8) 디더링을 합니다. 강도는 0..1이고 0이면 디더링 없음과 같습니다. 픽셀 하나가 바뀌어도 다른 픽셀의 결과는 바뀌지 않습니다. 오차 확산 방식은 아직 없습니다.
- `crates/gif-core/src/encode.rs`의 `encode_gif`가 RGB 프레임을 받아 팔레트 → 디더링 → 차분 → 압축을 한 번에 수행하는 순수 함수입니다. 설정은 `ManualSettings { colors: 2..=255, dither: 0..=1 }`입니다. `lossy`와 `maxSize` 모드는 아직 없고, 생기면 스케치의 `EncodeSettings` 합 타입으로 묶습니다.
- `app`(Tauri 2)과 `ui`(빌드 도구 없는 정적 HTML/JS)가 생겼습니다. 지금은 샘플 영상을 `encode_gif`로 만들어 창에 보여 주는 명령 `make_sample_gif` 하나뿐입니다. 화면이 커지면 TypeScript와 번들러를 도입합니다.
- `crates/gif-win`의 `ScreenCapturer`가 DXGI Desktop Duplication으로 모니터 하나를 열고, `capture(region)`이 그 영역의 RGB 픽셀을 돌려줍니다. 화면이 안 바뀌어 새 프레임이 없으면 마지막으로 받은 화면을 다시 씁니다. `ScreenRect`의 x, y는 그 모니터의 왼쪽 위를 (0, 0)으로 하는 물리 픽셀이고, `MonitorId`는 DXGI가 모니터를 나열하는 순서입니다. 실제 화면(2560×1440 주 모니터)에서 캡처되는 것을 확인했습니다. 복제를 연 직후의 첫 프레임은 `LastPresentTime`이 0이고 그림이 비어 있어서(전부 검정), 화면이 실제로 다시 그려진 프레임만 받아 둡니다. 회전된 모니터, `ACCESS_LOST` 복구, 해상도 축소는 아직 없습니다.
- `gif-core`의 `schedule::frame_due(fps, index)`가 녹화 시작부터 잰 각 프레임의 예정 시각을 돌려줍니다. `gif-win`의 `record_screen`은 프레임마다 그 시각까지 기다렸다가 캡처합니다. 간격을 더해 가지 않고 시작 시각에서 매번 다시 계산하므로 캡처가 늦어도 밀림이 쌓이지 않습니다. 루프는 프레임마다 기다린 뒤에 `keep_going()`을 묻고, 거짓이면 그 프레임을 찍지 않고 끝냅니다. 프레임 수 상한(`max_frames`)에 닿아도 끝납니다. 프레임은 모두 메모리에 둡니다.
- `gif-core`의 `selection::drag_region(monitor, monitor_size, from, to)`이 누른 점과 뗀 점을 녹화 영역으로 바꿉니다. 어느 방향으로 끌어도 같은 사각형이 되고, 모니터 밖으로 나간 부분은 가장자리에서 자르며, 한 변이 16픽셀보다 작으면 선택이 아닙니다(클릭은 무시).
- `gif-win`의 `select_region(monitor)`이 선택 오버레이입니다. 모니터 전체를 덮는 최상위 Win32 창(`WS_EX_LAYERED`)을 띄워 화면을 어둡게 하고, 드래그한 사각형은 색상 키로 뚫어 원래 밝기로 보여 줍니다. 왼쪽 버튼을 떼면 영역을 돌려주고, Esc나 오른쪽 클릭이면 `None`입니다. 이 함수는 호출한 스레드에서 메시지 루프를 돌며 끝날 때까지 기다립니다. 스레드를 Per-Monitor v2로 바꾼 뒤 창을 만들기 때문에 창 좌표가 곧 물리 픽셀이고, 좌표 변환은 여기에만 있습니다. 오버레이는 영역을 돌려주기 전에 없애므로 `WDA_EXCLUDEFROMCAPTURE` 없이도 첫 캡처에 찍히지 않습니다(테스트로 확인).
- 앱의 `Recorder`(`app/src/screen.rs`)가 녹화 한 번의 단계(`Idle → Selecting → Recording → StopAsked | CancelAsked → Encoding → Idle`)를 뮤텍스 하나로 소유합니다. 명령은 `record_screen_gif`(영역 선택부터 GIF까지 기다렸다가 돌려줌), `stop_recording`, `cancel_recording` 셋입니다. 드래그가 끝나면 바로 녹화가 시작되고(`immediate`의 시작 규칙), 그 순간 `recording-started` 이벤트로 영역 크기를 페이지에 알려 버튼이 [끝]으로 바뀝니다. 선택이나 녹화를 취소하면 빈 응답을 돌려줍니다. 녹화 중에 다시 시작하면 거절합니다. 프레임을 메모리에 두기 때문에 길이 상한은 30초와 "프레임 합계 1GiB" 중 짧은 쪽입니다(2560×1440, 30fps면 97프레임). 아직 주 모니터만 고를 수 있습니다. `Recorder`의 단계는 `gif-core`의 `SessionState`와 아직 따로입니다. `recordControl`·`selection` 설정이 들어올 때 합칩니다.
- 녹화가 시작되기 전의 취소: 드래그를 끝낸 뒤 화면 캡처를 열고 임시 파일을 만드는 동안(측정한 날 0.3~0.6초)에는 단계가 아직 `Selecting`입니다. 전에는 `stop`과 `cancel`을 `Recording`일 때만 받아서 이때의 취소가 버려졌고, 녹화가 그대로 시작됐습니다. 이제 `cancel`은 `Selecting`일 때도 `CancelAsked`로 적어 둡니다. 녹화로 넘어가는 곳(`start_recording`)은 단계가 `Selecting`일 때만 `Recording`으로 바꾸고, 아니면 아무것도 찍지 않고 "취소됨"으로 끝냅니다. `stop`은 여전히 `Recording`일 때만 받습니다(찍은 것이 없는데 끝낼 수는 없음). 선택 중의 Esc는 전처럼 오버레이를 닫아 취소하고, 이제 같은 순간에 `CancelAsked`도 적히므로 오버레이가 막 닫힌 직후에 눌러도 취소됩니다. 실제 앱에서 드래그 뒤 0, 30, 80, 150ms에 Esc를 누르면 녹화가 시작되지 않고 취소되며, 300ms 이후에는 녹화가 시작된 뒤 취소되는 것을 확인했습니다.
- `gif-win`의 `Hotkeys`가 전역 단축키를 맡습니다. 전용 스레드 하나가 `RegisterHotKey`로 등록하고 메시지 루프에서 `WM_HOTKEY`를 받아 콜백을 부릅니다. 등록과 해제는 등록한 스레드에서만 할 수 있어서, 다른 스레드의 `register`/`unregister` 호출은 채널에 요청을 넣고 그 스레드를 깨우는 방식입니다. `Hotkeys`를 버리면 스레드가 잡고 있던 단축키를 모두 놓습니다. `KeyCombo::from(Hotkey)`가 설정값을 Win32 수식키 비트와 가상 키 코드로 바꿉니다.
- 앱은 시작할 때 `Win+Shift+G`를 등록하고, 눌리면 Rust가 저장된 설정(`settings.json`)으로 바로 녹화를 시작합니다(아래 "트레이 상주" 참고). 등록에 실패하면 페이지에 그 사실을 표시하고 버튼으로만 시작합니다. Esc는 선택을 시작할 때, Enter는 녹화가 시작될 때 등록하고 끝나면 둘 다 해제합니다. 그래서 녹화하지 않을 때는 다른 프로그램의 Enter와 Esc를 가로채지 않습니다. 선택 중의 Esc는 `cancel_selection()`이 오버레이 창에 닫기 메시지를 보내 취소합니다(오버레이가 키보드 포커스를 못 얻은 경우에도 동작). 단축키 변경 UI는 아직 없습니다.
- 녹화한 GIF는 인코딩이 끝나면 `사진\midi\midi-YYYYMMDD-HHMMSS.gif`로 자동 저장됩니다. `gif-core`의 `output::gif_file_name`이 이름을 정하고(같은 초에 또 저장하면 `-2`, `-3`…을 붙여 기존 파일을 덮어쓰지 않음), 앱의 `save::save_gif`가 `.part` 파일에 쓴 뒤 이름을 바꿔서 쓰다 만 GIF가 남지 않게 합니다. 저장 결과는 `gif-saved` 이벤트로 페이지에 알리고, 실패해도 미리보기는 그대로 보여 줍니다. [폴더에서 보기]는 탐색기에서 그 파일을 선택해 엽니다. 저장 폴더를 바꾸는 설정과 클립보드 복사는 아직 없습니다. 샘플 GIF는 저장하지 않습니다.
- 폼의 선택(fps, 크기, 화질 단계, 용량 목표, 디더링 강도)은 `%APPDATA%\com.midi.app\settings.json`에 저장되고 다음 실행 때 폼에 다시 채워집니다. 저장하는 값은 녹화를 시작할 때 Rust로 보내는 `settings::RecordSettings`와 같은 타입이라, 저장용 형식이 따로 없습니다. 폼의 값이 바뀔 때마다 페이지가 `remember_settings`를 부르고, `settings::store`가 `.part` 파일에 쓴 뒤 이름을 바꿉니다. 앱을 열면 페이지가 `saved_settings`로 받아 폼에 채웁니다. 기본값(15fps, 영역 그대로, 자동, 용량 목표 없음, 디더링 1)은 `RecordSettings::default()` 한 곳에 있습니다. `settings::load`는 파일이 없거나, JSON으로 읽히지 않거나, 지금의 규칙으로 녹화를 시작할 수 없는 값(`can_record()`가 거짓)이면 통째로 기본값을 돌려주고, 파일에 없는 항목만 그 항목의 기본값으로 채웁니다. 녹화를 시작할 수 없는 값(예: 가로 0)은 저장하지 않으므로 파일에는 마지막으로 쓸 수 있었던 설정이 남습니다. 크기와 화질 단계를 둘 다 정해 용량 목표 칸이 꺼진 동안에는 용량 목표를 "없음"으로 저장합니다. 단축키와 저장 폴더는 아직 설정이 아니어서 저장하지 않습니다.
- 트레이 상주(`app/src/tray.rs`): 앱이 뜨면 트레이 아이콘을 만듭니다. 창의 [X]는 앱을 끄지 않고 창을 숨기며, 그 실행에서 처음 숨길 때 "트레이에서 계속 실행됩니다" 알림을 한 번 띄웁니다. 트레이 왼쪽 클릭은 녹화 중이면 끝내기(`Recorder::stop`이 받아들였는지 돌려줌), 아니면 녹화 시작입니다. 더블클릭 동작은 두지 않습니다(한 번 클릭이 늦어지는 함정, 7장). 오른쪽 메뉴는 [영역 골라 녹화], [창 열기], [저장 폴더 열기], 구분선, [종료]입니다. 툴팁은 상태에 따라 `대기`, `녹화하는 중 (클릭하면 끝냅니다)`, `GIF 만드는 중 45%`(두 번째 시도부터 시도 번호)로 바뀌고, 녹화가 어떻게 끝나든 가드가 대기 문구로 되돌립니다. 창이 숨겨져 있을 때만 저장·실패를 Windows 알림(`tauri-plugin-notification`)으로 알립니다. 창이 보이면 페이지가 알려 주므로 띄우지 않습니다. 녹화 시작은 이제 Rust가 합니다: 버튼, 단축키, 트레이 모두 `start_recording`으로 가고, 녹화는 별도 스레드에서 돕니다. 버튼은 폼의 현재 설정을 넘기고, 단축키와 트레이는 저장된 설정을 씁니다. 페이지는 `selection-started`, `recording-started`, `gif-progress`, `gif-encoded`, `gif-saved`, `recording-finished`(저장됨/취소됨/실패) 이벤트로 화면만 바꾸고, 미리보기는 `last_gif` 명령으로 받습니다. 전에는 단축키가 페이지의 버튼을 대신 눌렀는데, 창이 숨겨지면 WebView의 스크립트가 늦게 돌거나 멈춰서 녹화가 시작됐다 안 됐다 했기 때문에 바꿨습니다. 확인한 것: 창을 닫아 숨긴 뒤 Win+Shift+G → 드래그 → Enter로 GIF가 저장되고(15fps라 프레임 시간 6, 7, 7), 트레이 클릭으로 선택 화면이 뜨고 Esc로 취소됩니다. 스크립트로 보낸 트레이 클릭은 아이콘이 숨김 영역(^)에 있으면 트레이 라이브러리(`tray-icon`)가 아이콘 위치를 얻지 못해 버립니다(실제 마우스 클릭은 숨김 영역이 열린 상태라 해당 없을 것으로 봄, 미확인). 메뉴 항목, 녹화 중 트레이 클릭으로 끝내기, 알림이 실제로 보이는지는 직접 확인하지 못했습니다. Windows 시작 시 실행과 앱 두 번 실행 막기는 아직 없습니다.
- 녹화 길이의 한도는 앱의 `screen::recording_limit(fps, 저장 크기, 임시 폴더 디스크의 여유 공간)`이 정합니다: 30초와 "여유 공간에서 1GiB를 남기고 프레임이 들어가는 길이" 중 짧은 쪽이고, 어느 쪽이 정했는지를 `LimitedBy::{Time, Disk}`로 함께 돌려줍니다. 한 프레임도 들어갈 자리가 없으면 녹화를 시작하지 않고 이유를 알립니다. 여유 공간을 알 수 없으면 시간 한도만 씁니다. 여유 공간은 `gif_win::free_disk_bytes`(GetDiskFreeSpaceExW)로 읽습니다. 녹화가 시작되면 `recording-started` 이벤트에 한도(밀리초)와 그 이유를 실어 보내고, 페이지는 남은 시간을 초 단위로 표시합니다. 디스크 때문에 30초보다 짧으면 처음부터 "디스크 여유 공간 때문에 최대 N초"를 같이 보여 줍니다. 녹화가 누구의 요청도 없이 끝났으면(루프가 끝났는데 상태가 아직 `Recording`) 한도에 닿은 것이므로 `Recorded { encoded, ended_at_limit: true }`를 돌려주고, 페이지는 결과 아래에 그 사실과 이유를 적습니다. 최대 길이 설정은 아직 없습니다.
- 인코딩 시간, 색 찾기 표를 넣기 전(2026-11-22 측정, 릴리스 빌드, `cargo run --release -p gif-win --example encode_time -- 가로 세로 fps 프레임수 [still|scroll]`): 처리량은 화질 1단계에서 초당 약 2.6메가픽셀, 6단계에서 약 10~14메가픽셀이고 크기와 무관하게 일정합니다. 300×200 30초(30fps, 900프레임)는 1단계 약 21초·6단계 약 5초, 1280×720 10초(15fps)는 약 54초·14초, 2400×1400 3.5초(30fps)는 약 136초·34초입니다. 1단계 시간의 약 90%가 디더링 단계(픽셀마다 팔레트에서 가장 가까운 색 찾기)이고, 그 시간은 팔레트 색 수에 거의 비례합니다(255색 120초, 32색 18초). 나머지는 팔레트 고르기 약 4%, 차분과 압축 약 7%(화면이 안 바뀌면 1% 미만), 잡음 제거 1% 미만입니다. 화면이 전혀 바뀌지 않아도 디더링 시간은 같습니다(바뀌지 않은 픽셀도 다시 계산). 모든 단계는 코어 하나만 씁니다.
- 색 찾기 표: `Palette::lookup()`이 돌려주는 `NearestColor`가 RGB 색 1,677만 개마다 한 칸(1바이트, 합계 16MB)인 표를 들고, 처음 물어본 색만 `Palette::nearest`로 팔레트 전체를 훑어 답을 적어 둡니다. 다시 물어본 색은 표에서 바로 읽습니다. 답은 `nearest`가 낸 것 그대로이므로 GIF의 내용은 표를 넣기 전과 같습니다. 팔레트는 255색까지라 번호 255가 "아직 안 물어봄" 표시입니다. `ordered_dither`는 이 표를 받고, `encode_gif`는 표 하나를 모든 프레임에 씁니다. 같은 예제로 다시 잰 결과(스크롤, 1단계): 300×200 30초는 21초 → 3.7초, 1280×720 10초는 54초 → 11초, 2400×1400 3.5초는 136초 → 23초이고, 디더링 단계만 보면 120초 → 2.8초입니다. 1단계와 6단계의 시간 차이는 거의 없어졌습니다. 이제 남은 시간은 차분과 압축 약 52%, 팔레트 고르기(모든 픽셀의 색 세기) 약 33%, 디더링 약 12%입니다. 화면이 안 바뀌는 녹화에서는 팔레트 고르기가 약 65%입니다. 측정할 때마다 화면 내용이 달라 파일 크기는 서로 비교할 수 없습니다.
- 색 세기: `Palette::from_frames`가 색마다 몇 픽셀인지 셀 때도 사전(HashMap) 대신 RGB 색마다 한 칸인 표(`u32` 1,677만 칸, 64MB)를 씁니다. 표를 앞에서부터 읽으면 색이 이미 정렬된 순서로 나오므로 따로 정렬하지 않습니다. 고르는 팔레트는 전과 같습니다. 한 색이 약 42억 픽셀을 넘으면 그 색의 개수는 거기서 멈춥니다(지금의 녹화 한도에서는 전체 픽셀이 그보다 적어 일어나지 않음). 다시 잰 결과(스크롤, 1단계): 팔레트 고르기 7.7초 → 0.5초, 전체는 300×200 30초 3.7초 → 2.2초, 1280×720 10초 11초 → 6.0초, 2400×1400 3.5초 23초 → 12.7초(화면이 안 바뀌면 12초 → 4.3초). 이제 스크롤하는 화면에서는 차분과 압축이 약 73%, 디더링 18%, 잡음 제거 6%, 팔레트 4%이고, 안 바뀌는 화면에서는 디더링이 약 52%입니다.
- 진행률: `encode::encode_frames`가 프레임 하나를 읽어 처리할 때마다 `Progress { done, total }`을 알립니다. 프레임을 두 번씩 읽으므로 `total`은 프레임 수의 두 배입니다. `encode_gif`는 알림 없이 같은 일을 하는 얇은 래퍼입니다. `fit::encode`는 `Step { attempt, progress }`를 알립니다. `attempt`는 1부터 세는 인코딩 횟수로, 용량 목표 때문에 다시 인코딩할 때마다 늘고(최대 6) 진행률은 0부터 다시 시작합니다. 몇 번을 하게 될지는 미리 알 수 없어서 전체 진행률 하나로 합치지 않습니다. 앱의 `Recorder::record`는 콜백 하나로 `RecordingEvent::Started`와 `RecordingEvent::Encoding(step)`을 알리고, `main`은 퍼센트가 바뀔 때만 `gif-progress` 이벤트(시도 번호, 퍼센트)를 보냅니다. 페이지는 `GIF로 만드는 중… 45%`, 두 번째 시도부터는 `(용량 목표에 맞추는 중, N번째 시도)`를 붙여 보여 줍니다. 첫 `gif-progress`를 받으면 남은 시간 표시를 멈추므로, Enter 단축키나 한도로 끝난 녹화도 곧바로 진행률로 바뀝니다. 샘플 GIF는 진행률을 보내지 않습니다.
- 프레임을 한 장씩 읽는 인코더(디스크 스풀의 첫 단계): `encode::encode_frames`는 프레임 묶음 대신 `FrameSource`(`frame_count()`, `read_frame(index, &mut 버퍼)`)를 받습니다. 프레임을 두 번 훑습니다. 첫 번째는 잡음 제거(`Stabilizer`)를 거친 색을 세어(`ColorCounts`) 팔레트를 고르고, 두 번째는 다시 잡음 제거 → 디더링 → `GifWriter::add_frame`으로 파일에 씁니다. 한 번에 들고 있는 것은 읽은 프레임 한 장, 화면에 보이는 프레임 한 장, 직전에 쓴 프레임의 색 번호 한 장과 두 표(64MB, 16MB)뿐이라, 인코더의 메모리 사용은 녹화 길이와 무관합니다. `stabilize`, `Palette::from_frames`, `write_gif`는 이 조각들 위에 얹은 함수로 남아 있고 결과는 전과 같습니다. 메모리에 있는 프레임 묶음(`&[&[Rgb]]`)도 `FrameSource`입니다. 용량 목표로 크기를 줄일 때는 `fit`의 `Shrunk`가 원본 소스를 감싸 읽을 때마다 줄입니다(줄인 프레임을 전부 만들어 두지 않음). 읽지 못한 프레임은 `EncodeError::FrameUnreadable { frame }`이 됩니다. 측정(릴리스, 1단계, 예제가 프레임 약 1,020MB를 직접 들고 있는 상태): 2400×1400 106프레임의 최대 메모리 2,520MB → 1,196MB, 1280×720 150프레임 1,026MB → 516MB. 시간은 14.7초 → 14.2초로 사실상 같습니다.
- 디스크 스풀(두 번째 단계): 녹화한 프레임은 메모리에 쌓지 않고 `gif_win::Spool`이 Windows 임시 폴더의 `midi-recording-<프로세스>-<번호>.frames` 파일에 이어 씁니다(처음에는 프레임을 통째로 썼고, 아래의 "바뀐 줄만 쓰기"로 바뀜). `gif_win::record_screen`은 프레임 묶음을 돌려주는 대신 찍을 때마다 받은 함수(`keep`)에 넘깁니다. `Spool`은 `FrameSource`라서 인코더가 그 파일에서 한 장씩 읽습니다. 파일은 `FILE_FLAG_DELETE_ON_CLOSE`로 열어서, 녹화가 끝나든 취소되든 앱이 죽든 핸들이 닫히면 Windows가 지웁니다. 쓰기에 실패하면 녹화를 멈추고 이유를 알립니다(그때까지 찍은 것으로 GIF를 만들지는 않음). 이제 녹화 길이는 메모리와 무관하고, 2560×1440에 30fps도 30초(약 10GB)까지 됩니다. 측정(2026-11-22, 릴리스, `cargo run --release -p gif-win --example spool_speed -- 가로 세로 fps 프레임수`): 1280×720 30fps(83MB/s)와 2560×1440 15fps(167MB/s)는 제때 찍힙니다. 2560×1440 30fps(332MB/s)는 이 PC에서 제때 될 때도 있고 밀릴 때도 있습니다(300프레임이 10초 대신 12.3초, 900프레임이 30초 대신 43.7초 걸린 적이 있음). 밀리면 프레임 수는 그대로인데 실제로 걸린 시간이 길어지므로, GIF가 실제보다 빠르게 재생되고 남은 시간 표시가 0이 된 뒤에도 녹화가 이어집니다. 실제 앱(릴리스)에서 2400×1400 30fps를 8초 녹화해 GIF가 나오고 임시 파일이 지워지는 것을 확인했습니다.
- 바뀐 줄만 쓰기: `Spool::push`는 직전 프레임과 줄 단위로 비교해 바뀐 줄만 파일에 씁니다. 바뀐 줄은 이어진 구간들(`runs`)로 묶고, 구간 사이의 안 바뀐 줄은 쓰지 않습니다. 첫 프레임은 통째로, 아무것도 안 바뀐 프레임은 0바이트입니다. 프레임마다 "어느 줄들이 바뀌었고 파일의 어디서 시작하는지"를 메모리의 목록(`changes`)에 둡니다. 읽을 때는 스풀이 들고 있는 한 장(`shown`)에 바뀐 줄을 차례로 덮어써서 그 프레임을 만듭니다. 인코더처럼 0번부터 순서대로 읽으면 프레임마다 그 프레임의 바뀐 줄만 읽고, 앞 번호로 돌아가면 0번부터 다시 덮어씁니다. 쓰는 쪽의 "직전 프레임"과 읽는 쪽의 "지금 보이는 프레임"은 같은 버퍼입니다. 녹화 한도는 여전히 프레임을 통째로 쓰는 최악의 경우로 계산합니다. 측정(2026-11-22, 릴리스, 2560×1440 30fps, 이 대화 창이 떠 있는 실제 화면): 300프레임에 3,318MB 대신 662~737MB, 900프레임에 9,953MB 대신 2,181MB를 썼고 세 번 모두 제때 찍혔습니다(가장 느린 쓰기 10ms). 모든 줄이 매 프레임 바뀌게 한 최악의 경우에는 줄어들지 않고 여전히 밀립니다(300프레임이 10초 대신 15.3초). 그때의 재생 속도는 아래의 "칸 번호"로 맞춥니다. 실제 앱(릴리스)에서 2400×1400 30fps 8초 녹화, 취소, 작은 영역 녹화가 동작하고 임시 파일이 지워지는 것을 다시 확인했습니다.
- 늦은 프레임과 재생 속도(칸 번호): 녹화 시간을 fps 간격의 칸(slot)으로 나누고, 칸 `n`의 예정 시각은 `schedule::frame_due(fps, n)`입니다. 녹화 루프(`record_frames`)는 프레임 하나를 찍어 넘긴(스풀에 쓴) 뒤 지금 시각이 속한 칸을 `schedule::slot_at`으로 구하고, 다음 칸과 그 칸 중 뒤의 것으로 갑니다. 그래서 쓰기가 늦으면 지나간 칸은 건너뛰고 지금 칸을 바로 찍습니다. 루프는 칸 수(`max_slots`, 30초 또는 디스크 한도)에서 끝나므로, 늦어도 녹화가 예정보다 길어지지 않고 남은 시간 표시와 맞습니다. 찍은 프레임은 칸 번호와 함께 넘어가고(`keep(frame, slot)`), `Spool`이 프레임마다 칸 번호를 적어 둡니다(앞 칸보다 뒤가 아니면 거절). `FrameSource::slot(index)`로 인코더가 읽고, 프레임 `i`는 자기 칸부터 다음 프레임의 칸 직전까지 보이도록 `delay::slots_delay(fps, 칸 범위)`의 시간이 GIF에 적힙니다(마지막 프레임은 한 칸). 칸 범위의 시간은 칸 시작 시각의 차라서, 건너뛴 칸이 있어도 1초 분량은 정확히 100(1/100초)입니다. 메모리의 프레임 묶음과 샘플은 칸 번호가 프레임 번호와 같아서 전과 같은 GIF가 나옵니다. 측정(2026-11-22, 릴리스, `spool_speed`): 1280×720 30fps에 10프레임마다 150ms를 일부러 멈추게 하면 300칸 중 231프레임을 찍고 9.99초에 끝나며, GIF는 10.00초 동안 재생됩니다. 이날은 2560×1440 30fps의 모든 줄이 바뀌는 녹화도 디스크가 따라가서 900칸 중 898~899프레임, 재생 30.00초였습니다. 실제 앱에서 300×200 30fps 녹화의 프레임 시간이 3, 3, 4로 전과 같은 것을 확인했습니다.
- **크기** 설정: `gif-core`의 `resize::OutputSize`는 `Original`(드래그한 영역 그대로) 또는 `FitWithin { width, height }`입니다. `for_source(width, height)`가 비율을 유지한 채 지정한 가로×세로 안에 들어가는 가장 큰 크기를 돌려줍니다(800×500을 480×270 안에 넣으면 432×270). 영역이 이미 더 작으면 키우지 않습니다. `resize::downscale`이 출력 픽셀 하나에 대응하는 원본 픽셀 묶음의 평균(반올림)으로 줄이고, 묶음은 `index × 원본 ÷ 출력`으로 나눠서 원본 픽셀이 빠지거나 겹치지 않습니다. `record_screen`이 프레임을 찍자마자 줄여서 보관하므로 메모리 상한(1GiB)과 인코딩 시간도 출력 크기를 따릅니다. 가로×세로로 지정한 크기는 용량 목표가 있어도 바뀌지 않습니다. "드래그한 영역 그대로"로 두면 용량 목표를 맞추려고 인코딩 단계에서 더 줄어들 수 있습니다.
- 열화 정도(`ManualSettings.tolerance`, 0~32)는 화질 단계가 정하는 값입니다(폼에 따로 나오지 않음). `gif-core`의 `stabilize::stabilize(frames, tolerance)`가 각 픽셀을 **지금 화면에 보이는 색**과 비교해서, 세 채널 모두 차이가 tolerance 이하면 화면의 색을 그대로 둡니다. 바로 앞 프레임이 아니라 화면의 색과 비교하므로 조금씩 계속 변하는 픽셀도 차이가 tolerance를 넘는 순간 따라갑니다. `encode_gif`가 팔레트를 만들기 전에 이 단계를 거치고, 디더링이 위치 고정이라 같은 색은 같은 번호가 되어 프레임 차분이 그 픽셀을 투명으로 처리합니다. gifsicle의 lossy LZW와는 다른 방식입니다(그쪽은 압축 단계에서 비슷한 번호열을 재사용). 실제 화면 480×270, 15fps 3초 녹화에서 0 → 272,680바이트, 4 → 123,687, 8 → 102,767, 16 → 78,377바이트였습니다. - 용량 목표가 생겼습니다. `gif-core`의 `fit::EncodeSettings`가 스케치의 합 타입입니다: `Manual(ManualSettings)` 또는 `MaxSize { max_bytes, dither }`. `fit::encode`가 둘을 받아 `Encoded { gif, width, height, fitted }`를 돌려줍니다. `MaxSize`는 화질 단계 10개(`LADDER`: 크기 100%·255색·열화 0부터 25%·16색·열화 24까지)에서 목표 이하가 되는 가장 좋은 단계를 찾습니다. 먼저 최고 단계를 해 보고(맞으면 한 번으로 끝), 다음에 최저 단계를 해 보고(그래도 크면 그 결과를 `fits: false`로 돌려줌), 그 사이를 이분 탐색하므로 인코딩은 많아야 6번입니다. 단계가 낮을수록 파일이 작다고 가정합니다. 크기 단계는 메모리의 프레임을 `downscale`로 다시 줄이므로 출력 크기가 녹화 해상도보다 작아질 수 있습니다. 앱 폼의 [용량 목표](없음, 1, 2, 5, 8, 10MB)가 이 설정이고, 목표를 고르면 색 수와 열화 정도 슬라이더는 쓰이지 않습니다(디더링 강도는 쓰임). 어느 단계로 만들었는지와 목표를 못 맞춘 경우를 `gif-fitted` 이벤트로 페이지에 표시합니다.
- **화질 단계**와 **용량 목표**: `gif-core`의 `fit::LEVELS`가 화질 단계 6개입니다(1단계 255색·열화 0, 2단계 255색·열화 4, 3단계 255색·열화 8, 4단계 128색·열화 8, 5단계 64색·열화 12, 6단계 32색·열화 16). `fit::Quality`는 `Level(1..=6)`(용량 목표 없음) 또는 `WithinBytes { max_bytes, adjust }`입니다. `adjust`는 용량을 맞추려고 무엇을 바꿔도 되는지를 뜻합니다: `Level`(크기 고정, 단계를 내림), `Size { level }`(단계 고정, 크기를 줄임), `LevelThenSize`(둘 다 자동, 단계를 6단계까지 내린 뒤에 크기를 줄임). 크기는 100%에서 90, 80, 70, 60, 50, 40, 33, 25%로 줄이고 25%가 하한입니다. `adjust`마다 "좋은 것부터 나쁜 것까지"의 후보 목록을 만들고(최대 14개), 같은 `first_fitting` 탐색으로 목표 이하인 가장 좋은 후보를 고릅니다. 먼저 첫 후보를 해 보고(맞으면 한 번으로 끝), 다음에 마지막 후보를 해 보고(그래도 크면 그 결과를 `within_limit: Some(false)`로 돌려줌), 그 사이를 이분 탐색하므로 인코딩은 많아야 6번입니다. 뒤 후보일수록 파일이 작다고 가정합니다. `fit::encode`는 `Encoded { gif, level, width, height, within_limit }`를 돌려줍니다. 앱의 `choice::QualityChoice::settings(size_is_fixed)`가 폼의 값을 이 타입으로 바꿉니다: 크기를 가로×세로로 지정했으면 크기 고정, 단계를 직접 골랐으면 단계 고정이고, 둘 다 고정이면 조정할 것이 없으므로 폼에서 용량 목표 칸을 끄고 Rust도 이유와 함께 거절합니다. 샘플 GIF는 크기를 자동으로 봅니다. 단계 목록은 `quality_levels` 명령으로 Rust에서 받아 폼에 채웁니다. 결과 아래에 실제 크기(줄였으면 `300×200 → 180×120`)와 쓰인 단계를 표시하고, 끝까지 낮춰도 목표를 넘으면 그 사실과 함께 "더 짧게 녹화"(크기 고정이면 "크기를 줄이거나"도)를 안내합니다. 색 수와 열화 정도를 직접 조절하는 슬라이더는 없앴습니다. 디더링 강도는 남아 있습니다.
- 아직 없는 것: `done`, `failed` 상태, `recording`의 시작 시각과 프레임 수, `encoding`의 진행률, 효과 목록. 캡처와 인코더 단위에서 추가합니다.

## 7. 참고 도구 조사 (2026-11-22)

남은 기능(녹화 틀, [시작]/[끝] 버튼, 트레이 상주)을 만들기 전에 ScreenToGif(2.43.2, C#/WPF, Ms-PL)와 ShareX(v18.0.1 WinForms, v22.4.0 Avalonia, C#, GPL-3.0)의 소스와 문서를 조사했습니다. 두 프로젝트 모두 코드는 가져오지 않고 방식만 참고합니다(ShareX는 GPL이라 코드를 섞으면 우리도 GPL이 됨). 아래 파일 경로는 각 저장소 기준입니다.

### 이미 같은 방향인 것

| 우리 | 참고 도구 |
|---|---|
| 프레임을 임시 파일에 쓰고 `FILE_FLAG_DELETE_ON_CLOSE`로 지움 | ShareX v22의 GIF 녹화가 같은 방식(`.이름.guid.frames`, `DeleteOnClose`, `ScreenRecordingLib/Encoding/GifWriter.cs`). ScreenToGif는 `%TEMP%\ScreenToGif\Recording\날짜\`에 프레임마다 PNG를 쓰고 5일 지난 폴더를 지움 |
| 전역 팔레트 하나 + 바뀐 부분만 쓰기 + 프레임마다 시간 | ShareX v22의 `GifWriter`가 같음 |
| 늦으면 지나간 칸을 건너뜀(칸 번호) | ShareX v22: 지난 칸은 건너뛰고 몰아 찍지 않음, 캐시 대기열이 차면 프레임을 버림(`ScreenRecordingLib/ScreenRecorder.cs`). ScreenToGif: 늦으면 바로 다음 프레임을 찍고 늘어난 간격을 그 프레임의 시간으로 씀 |
| 테두리는 영역 바깥 + `WDA_EXCLUDEFROMCAPTURE` | ShareX: 영역 바로 바깥에 1px 점선(대기·일시정지 노랑, 녹화 초록), 속이 빈 창. v22는 `WDA_EXCLUDEFROMCAPTURE`도 씀. ScreenToGif는 쓰지 않고 위치로만 피함 |
| 한 모니터 안에서만 녹화 | 두 도구 모두 영역이 모니터를 넘지 못함 |
| 단축키 등록 실패를 알림 | ShareX: 실패한 단축키 목록과 "다른 단축키를 고르거나 충돌하는 프로그램을 끄라"는 안내, 나중에 다시 시도 가능 |

### 가져올 것

1. **녹화 중 조작 패널은 포커스를 뺏지 않는 창(`WS_EX_NOACTIVATE`)**: ShareX는 패널이 전체 화면 게임의 포커스를 뺏는 문제가 보고됨(#7979). 우리 용도는 영상 플레이어라 같은 문제가 생기면 플레이어가 전체 화면에서 빠질 수 있음.
2. **패널에 남은 시간 표시**: 트레이로 숨어 있을 때는 메인 창이 안 보이므로, 남은 시간과 [끝]·[✕]는 영역 옆 패널에 있어야 함(ShareX는 패널에 타이머).
3. **패널 자리**: ScreenToGif 새 녹화기는 패널을 자리가 있는 쪽으로 옮김(`MoveCommandPanel`). 우리는 `WDA_EXCLUDEFROMCAPTURE` 덕분에 영역과 겹쳐도 GIF에는 안 찍히지만, 사용자 눈에는 영상을 가리므로 바깥 → 안쪽 모서리 순서로 둠(기존 설계 그대로).
4. **녹화 틀(`frame`)**: ScreenToGif 옛 녹화기(기본값)가 바로 이 방식. 창 자체가 속이 빈 틀이고 아래에 버튼 막대. 가장자리로 크기 조절, 가로·세로 숫자 입력, 화살표로 이동(Shift/Ctrl+화살표로 크기, Alt로 5px씩), 창 위로 끌어다 놓아 그 창에 맞추기. 위치·크기는 기본으로 기억하고, 새 녹화기는 영역과 함께 DPI 배율을 저장함. 우리도 **영역을 DPI 배율과 함께 저장**하고, 숫자 입력과 화살표 조절을 넣음.
5. **선택 오버레이의 크기 표시**: 두 도구 모두 선택 중에 크기(가로×세로)를 보여 줌. 돋보기는 ShareX 기본값이지만 우리 용도(영상의 일부)에는 덜 중요.
6. **트레이**: ShareX는 창을 닫으면 트레이로 숨고(처음 한 번 풍선 안내), 트레이 왼쪽 클릭이 영역 캡처, 더블클릭이 창 열기. ScreenToGif는 왼쪽 클릭이 창 숨기기/보이기, 더블클릭이 녹화기 열기. **더블클릭 동작을 정해 두면 한 번 클릭이 더블클릭 시간만큼 늦게 실행되는 함정**이 있음(ShareX). 시작 프로그램 등록은 ShareX가 시작 폴더 바로가기 + `-silent`(숨긴 채 시작, 작업 관리자의 "사용 안 함" 존중), ScreenToGif가 `HKCU\...\Run`.
7. **인코딩 진행률을 트레이에**: ShareX는 트레이 아이콘에 퍼센트를 보여 주고, 끝나면 소리와 함께 후속 작업(저장, 클립보드, 편집기 등).

### 우리 용도 때문에 다르게 할 것

- **선택 화면은 멈춘 스크린샷이 아니라 살아 있는 화면**: 두 도구 모두 영역 선택 때 화면을 멈춘 스크린샷을 배경으로 씀(ShareX는 살아 있는 화면 옵션도 있음). 우리는 재생 중인 영상의 일부를 고르므로, 지금처럼 살아 있는 화면 위에 어둡게 덮는 방식을 유지.
- **영상은 화면 전체가 계속 바뀜**: 용도가 영상이므로 "바뀐 줄만 쓰기"의 효과는 작고, 큰 영역·30fps에서는 디스크 쓰기가 핵심 병목이 될 수 있음. ShareX v22는 쓰기를 대기열 + 다른 스레드로 넘기고 대기열이 차면 프레임을 버림. 우리 칸 번호 방식 위에 같은 대기열을 얹는 것이 다음 후보.
- **기본 fps**: 두 도구 모두 GIF 기본값이 15fps(ShareX 영상은 30). 우리는 30. 15로 바꾸면 디스크와 인코딩 부담이 절반.
- **디더링**: ShareX(FFmpeg 경로)는 `palettegen=stats_mode=full` + `paletteuse=dither=sierra2_4a`(오차 확산). 영상은 그라데이션이 많아 오차 확산이 위치 고정 패턴보다 보기 좋을 수 있음. 화질 작업 때 비교 후보.
- **녹화가 끝난 뒤**: ScreenToGif는 저장하지 않고 편집기를 엶. ShareX는 저장 후 후속 작업. 우리는 지금처럼 바로 저장하고, 최종 목표(편집기)가 생기면 "편집기에서 열기"를 후속 작업으로 추가.
- **같은 단축키로 끝내기**: ShareX는 시작 단축키를 다시 누르면 끝남(시작 중에 누르면 취소). 우리는 2026-11-20 결정대로 Enter로 끝냄(5장 결정 기록 참고).

### 피할 것 (보고된 문제)

- 영역이 인코더의 최대 크기를 넘으면 파일도 오류도 없이 끝남(ShareX #8812, NVENC 4096). 우리 GIF는 가로·세로가 65535까지라 해당 없지만, 실패를 조용히 삼키지 않는다는 원칙은 유지.
- 세로(회전된) 모니터에서 Desktop Duplication 프레임이 돌아간 채 나옴(ScreenToGif 알려진 문제). 우리도 DXGI라 같은 문제가 있을 수 있음(1장의 "회전된 모니터는 아직 없음").
- 하이브리드 GPU에서 Desktop Duplication이 실패함(ScreenToGif가 전용 오류 창을 띄움). 우리도 실패 시 이유를 알려야 함.
- 녹화 창을 옮기면 녹화가 일시정지됨(ScreenToGif 옛 녹화기). 우리는 녹화가 시작되면 영역을 고정하므로 해당 없음.

### 정리한 구현 순서

1. **트레이 상주**: 창을 닫으면 트레이로, 트레이 왼쪽 클릭 = 영역 선택 시작, 오른쪽 메뉴(녹화 시작, 창 열기, 저장 폴더 열기, 종료), 더블클릭 동작 없음, 인코딩 진행률은 트레이 툴팁, 저장되면 Windows 알림. Windows 시작 시 실행은 설정(기본 꺼짐).
2. **녹화 중 패널**: 영역 옆의 작은 창(포커스 안 뺏음, 캡처 제외)에 남은 시간, [끝], [✕]. 트레이 모드에서 메인 창 없이 녹화를 끝낼 수 있게 됨. `recordControl: button`의 [시작]도 이 패널.
3. **녹화 틀(`selection: frame`)**: 지난 영역(DPI 배율 포함)을 기억했다가 틀로 띄우기, 가장자리·숫자·화살표로 조절.
